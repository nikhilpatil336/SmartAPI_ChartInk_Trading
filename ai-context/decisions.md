# Technical Decisions

## Testing Strategy (Sessions 30–33)
- **Unit tests are mandatory before every deploy** — a production incident (Session 29) caused the CAS-before-delta bug: an `open` WS event with `filledshares=0` permanently locked `tryBeginEntryOrders()`, so the subsequent `complete` event skipped SL+target placement entirely. `./mvnw test` must pass before deploying to the Pi.
- **49 unit tests across 13 test files** — 4 entry strategies (CAS/delta/stale), 4 exit fill strategies (tradeCompleted guard + cancel-fails error path with `withVirtualTime`), 4 exit open strategies (partial fill, companion-open cancel, stale delta, full-fill zero-remaining), `SquareOffManager` (LONG + SHORT netQty, CAS guard, concurrent calls, no-fills SHORT).
- **Verify `modifyStopLossOrder` with `eq(remainingQty)` in open strategies** — `safeModifyOrReplace(monoArg, fallback)` wraps a call to `executionService.modifyStopLossOrder(...)` to build the Mono argument. The `modifyStopLossOrder` method IS called eagerly (before subscription) to build the Mono. Verifying only `safeModifyOrReplace` is not enough — also verify `modifyStopLossOrder` with `eq(expectedQty)` to catch wrong-qty bugs. Applied in `SellOpenStrategyTest` C1/C2 and `ShortTargetOpenStrategyTest` SC1/SC2.
- **Full-fill path tests (remainingQty=0) in open strategies** — when `filledQty == ctx.getQuantity()`, `remainingQty = 0` and `processShortTarget`/`processSellFill` return `Mono.empty()` immediately. These tests require zero stubs (no tokenManager, no executionService, no orderActionExecutor calls). Added as C4 in `SellOpenStrategyTest` and SC4 in `ShortTargetOpenStrategyTest`.
- **Pure unit tests, no Spring context** — `@ExtendWith(MockitoExtension.class)` only; all dependencies are `@Mock`; real object under test via `@InjectMocks`. Runs in ~3 seconds with no `.env` or broker connection needed.
- **Stubs are per-test, not `@BeforeEach`** — Mockito strict stubbing throws `UnnecessaryStubbingException` if a stub is declared but not called (e.g., early-return tests don't call order placement mocks). Keeping stubs inside each test method avoids this.
- **`StepVerifier` is required to subscribe reactive chains** — `strategy.onFilled()` returns `Mono<Void>`; without `StepVerifier.create(...).verifyComplete()` the reactive chain never executes and tests pass vacuously.
- **`StepVerifier.withVirtualTime()` required for retry error paths** — `Retry.backoff(3, Duration.ofMillis(200))` takes ~1.4s real time; `withVirtualTime(() -> ...).thenAwait(Duration.ofSeconds(30))` fast-forwards all scheduled delays without wall-clock waiting.
- **`anyString()` does NOT match null — use `any()` for nullable variety params** — `ctx.getBuyVariety()` / `ctx.getSellVariety()` can be null in factories where variety is not set. Mockito strict mode with `anyString()` causes `PotentialStubbingProblem` when null is passed, which triggers `retryWhen` to fire extra times and causes `TooManyActualInvocations`. Fix: use `any()` for the variety parameter in `placeCancelOrder` stubs when variety may be null.
- **`stopLossRemainingQty(delta)` mutates internal state** — `remainingQty.addAndGet(-delta)` in `OrderContext`; factory must pre-seed `ctx.getRemainingQty().set(qty)` or the guard `remainingQty > 0` fails silently.
- **`LocalToSmartapiApplicationTests` deleted** — the Spring Initializr-generated `contextLoads()` test boots the full application context (requires `.env`, broker connections). Deleted in Session 30; never recreate it for this project.
- **Test helper factories in `src/test/.../helper/`** — `OrderContextFactory` has 10 methods covering entry (freshLong, freshShort, CAS-claimed variants), exit fill (longWithSellAndSlOpen, shortWithBuyAndSlOpen, shortSellOpenNotPartialFilled), and exit open (longReadyForSellOpenFill, longReadyForSlOpenFill, shortReadyForTargetOpenFill, shortReadyForSlOpenFill). `OrderStatusResponseFactory` has buyComplete, buyOpen, shortEntryComplete, shortEntryOpen.

## Authentication & Sessions
- **TOTP-based login via java-otp + googleauth** — AngelOne API mandates TOTP on every login; these libraries compute the time-based OTP from a secret key stored in `.env`.
- **JWT stored in file + held in memory** — `TokenStorageService` writes the JWT to `data/token/tokens.json` on login; on restart, `TokenManager.init()` reads it back and skips re-login if still valid.
- **Startup-only re-login; no periodic token refresh** — a `@Scheduled` 15-min refresh using the refresh token was written but commented out because AngelOne's refresh token API was unreliable; current approach re-logins on startup if the token is expired.
- **`synchronized` block in `refreshTokens()`** — prevents two concurrent threads from both detecting an expired token and attempting simultaneous logins.
- **No auth on incoming webhook endpoints** — acceptable; the Pi runs on a private home network and Chartink only POSTs to the URL you configure in their dashboard.

## Data Storage
- **File-based JSON, no database** — all state (tokens, scrip master, RMS, order context, SL store) lives in flat JSON files; avoids JPA/DB overhead on a Raspberry Pi where disk I/O is the bottleneck, not query complexity.
- **`OrderContext` persisted every 5 min + on JVM shutdown** — `OrderContextPersistenceScheduler` handles the interval; `ShutdownHandler` (@PreDestroy) triggers a final save so no active order context is lost if the process is killed cleanly.
- **`SlOrderStore` writes async via `CompletableFuture.runAsync()`** — fire-and-forget so file I/O never blocks the reactive order flow; errors are logged but not re-thrown (comment in source says "do NOT swallow").
- **`AlertStateRegistry` is in-memory only, not persisted** — first-alert state is inherently ephemeral (10-minute window); losing it on restart just causes the next incoming alert to start a fresh first-alert cycle.

## Configuration & Secrets
- **Secrets in `.env` only, loaded via dotenv-java** — `application.properties` references them as `${ANGEL_CLIENT_ID}` etc.; the `.env` file is never committed; this is the only secrets boundary in the app.
- **Single `ApplicationProperties` bean (`myapp.*`)** — all business config is centralized here; `@Value` is banned for business logic (one known exception in `ApplicationStartupService`) to make config discoverable in one place.
- **Dual path blocks in `application.properties` (Windows/Pi), manual comment swap** — no Spring profile-based path switching; deemed over-engineering for a two-machine setup where you always know which block to activate.
- **`fixedQuantityFlag` / `fixedQuantity` override** — when enabled, caps the leverage-calculated quantity at a fixed number (currently 5) to prevent over-trading during live strategy testing.
- **Dummy IP/MAC headers hardcoded in `application.properties`** — AngelOne API requires these headers syntactically but does not validate the values; real device info is not needed for this use case.

## Code Structure & Patterns
- **Scrip master map keyed by trading symbol, not company name** — `ScripMasterService.filterOnlyEquityNse` keys the `nseEquityMap` by `symbol.replace("-EQ", "")` (e.g., `SBILIFE`) rather than the `name` field (which AngelOne may store as the full company name). Chartink webhooks always send the NSE ticker, so the key must match the ticker. All callers (`handleSingleStockAlert`, `AlertAnalyticsService`, `HistoricalDataService`) pass Chartink tickers. If a stock is genuinely absent from the map, `tickSize` defaults to `applicationProperties.getDefaultTickSize()` (configured via `myapp.default-tick-size`, currently 10) and the downstream `symbolToken` null guard rejects the order gracefully.
- **Default tick size configurable via `myapp.default-tick-size`** — was hardcoded as `BigDecimal.TEN` in three fallback sites in `OrderService_v2`. Now reads from `ApplicationProperties.getDefaultTickSize()`. Default value is 10, matching old behaviour. Change in `application.properties` takes effect on restart without recompile.
- **Strategy pattern for WebSocket order events** — `FilledOrderHandler`/`OpenOrderHandler`/`RejectedOrderHandler` each look up the order's role in `OrderRegistry` and delegate to a per-role strategy (e.g., `BuyFilledStrategy`, `ShortStopLossFilledStrategy`); adding a new order type means adding a strategy class, not touching dispatch logic.
- **`PendingOrderEventStore` as a race-condition buffer** — WebSocket fill events can arrive before `registerBuy/Sell` has stored the `OrderContext` (broker confirms faster than the reactive chain completes); the store buffers those events and replays them inline immediately after registration.
- **`IOrderWebSocketConnector` interface + `@Profile` split** — `OrderWebSocketConnector` is `@Profile("prod")`; `DummyOrderWebSocketConnector` is `@Profile("test")`; lets you run the app locally without a live broker WebSocket.
- **`cloneRequestForSingleStock()` in multi-stock alert processing** — Chartink sends comma-separated stocks in one webhook; the handler uses `Flux.concatMap` over each stock, cloning the request per stock so downstream handlers get isolated name/price data.
- **`mapToOrderResult()` hardcodes `status = "COMPLETE"`** — the legacy v1 polling path (`chartinkBuyOrder`) assumed the order poll would return real status; hardcoding COMPLETE forces it to proceed immediately using the limit price instead of the average price. This bypasses polling and is intentional for the current workflow.
- **`OrderService` (v1) kept alive** — `OrderController.getOrderStatus()` still references it; all new logic is in `OrderService_v2`. The v1 service is dead code except for that one controller method.
- **`delta <= 0` check must come before `tryBeginEntryOrders()` in all entry strategies** — An `open` WS event with `filledshares=0` (order on exchange, not yet filled) passes `supports()` and enters `onFilled()`. If CAS is claimed before the delta check and delta=0, the method returns early but the CAS is permanently locked. The subsequent `complete` event (with real filled qty) then sees the CAS taken and skips — no SL+target placed. Rule: always compute `delta` and guard `if (delta <= 0) return Mono.empty()` **before** calling `tryBeginEntryOrders()`. Applied in `BuyOpenStrategy`, `ShortEntryOpenStrategy`, `BuyFilledOrderStrategy`, `ShortEntryFilledOrderStrategy`.
- **`tryBeginEntryOrders()` CAS guard prevents duplicate SL+target placement** — `open` (partial fill) and `complete` WS events can arrive within milliseconds of each other; both strategies pass `supports()` because `buyOrderId`/`stopLossOrderId` are only set in `doOnSuccess` after the HTTP response (~600ms). Added `AtomicBoolean entryOrdersPlacing` + `tryBeginEntryOrders()` to `OrderContext` (same CAS pattern as `tryStartExit()`). Added guard at the top of `onFilled` in `BuyOpenStrategy`, `BuyFilledOrderStrategy`, `ShortEntryOpenStrategy`, `ShortEntryFilledOrderStrategy`. The first path to CAS wins; the other returns `Mono.empty()` immediately.

## Backtest Design (Session 19 — Nifty benchmark)
- **Dual Nifty benchmark in SUMMARY sheet** — Two parallel columns: (1) "Beats Nifty (Actual)?" fetches real Nifty 50 1D candles via `CandleCacheService` for the exact alert date range (`minDate → maxDate` extracted from the deduped alert list), computes `(endClose - startClose) / startClose × 100`; (2) "Beats Nifty (Avg Pace)?" uses `12.5 × (days/365)` — no API dependency, works offline. Both answer different questions: actual measures what Nifty really did in that period; avg pace measures against the long-run market rate.
- **Nifty 50 token = `99926000` on AngelOne** — Token `26000` is accepted by the API but returns empty data for historical candles. `99926000` is the correct token for Nifty 50 index historical data. Configurable via `myapp.nifty-symbol-token` so it can be changed without recompile.

## Backtest Design (Session 19 audit fixes)
- **Expectancy = `avgPnlPerTrade`** — the old formula `(winRate × avgWinRR) - lossRate` mixed R:R (dimensionless ratio) with `lossRate` (fraction) and excluded squareoff outcomes entirely. Replaced with direct average P&L per trade across all outcomes (wins + losses + squareoffs). `avgWinRR` is kept as a secondary column for R-multiple reference.
- **Squareoffs count in `winRate` denominator** — squareoffs were already tracked in `tradesTaken` but excluded from winRate's denominator in the old formula. Now `winRate = wins / tradesTaken` where `tradesTaken` includes squareoffs; negative squareoffs also count toward `maxConsecutiveLosses`.
- **`maxDrawdown` + `maxConsecutiveLosses` added to `BacktestSummary`** — computed in `computeStats()` by iterating cumulative P&L. Drawdown = peak minus trough; consecutive loss run includes negative SQUAREOFF_EXIT outcomes. Both visible in SUMMARY Excel sheet.
- **`INSUFFICIENT_DATA` verdict when tradesTaken < 30** — strategies with fewer than 30 trades show `INSUFFICIENT_DATA` instead of PROFITABLE/LOSS-MAKING (constant `MIN_SAMPLE_SIZE = 30` in `BacktestSummary`). Statistically, <30 trades cannot distinguish edge from noise.
- **`targetAtrPeriod` in `StrategyConfig`** — previously `resolveTarget()` always used `slAtrPeriod` for the ATR key even for the target. Now `StrategyConfig.targetAtrPeriod` (Integer, null = fall back to `slAtrPeriod`) controls this independently. The ATR key in `buildIndicatorContext()` also uses `targetAtrPeriod`.
- **MACD/Supertrend/BB params configurable per strategy** — `StrategyConfig` now has `macdFastPeriod`, `macdSlowPeriod`, `macdSignalPeriod` (Integer), `supertrendMultiplier`, `bbStdDev` (Double). All default to null (framework defaults: 12/26/9, 3.0, 2.0). `computeIndicator()` accepts `StrategyConfig` and uses these params so two strategies can test different MACD/ST/BB variants without changing code.
- **In-sample / out-of-sample date split via `POST /backtest/run-historical`** — added optional `?fromDate=YYYY-MM-DD` and `?toDate=YYYY-MM-DD` query params. Running with `?toDate=X` gives in-sample; running with `?fromDate=X+1` gives out-of-sample. `readAlerts()` unified to handle exactDate, fromDate, toDate filtering in one method.

## Backtest Design
- **`Candle.getTime()` annotated `@JsonIgnore`** — `getTime()` returns a `LocalDateTime` derived lazily from the `timestamp` string. The plain `new ObjectMapper()` in `CandleCache` has no JSR310 module; serializing this field caused all cache saves to fail silently. Solution: ignore it in JSON — it is always re-derived from `timestamp` on first access. No data loss; cache files are smaller.
- **Backtest charges expressed as % of entry price, brokerage configurable** — statutory charges (STT 0.025% sell, NSE exchange 0.00325% both sides, SEBI 0.0001% both sides, stamp duty 0.003% buy, GST 18% on brokerage+exchange+SEBI) are hardcoded as constants since they are regulated rates. Brokerage is configurable via `myapp.backtest-brokerage-pct` (default `0.0`) because it varies per broker plan. All charges are expressed as % of entry price to be directly comparable to `pnlPct`.
- **`takeAllLong` / `takeAllShort` flags bypass condition evaluation** — `ConfigurableBacktestStrategy.evaluate()` returns `false` for empty condition lists (no conditions = no signal). To support "take every alert unconditionally" strategies, `StrategyConfig` has boolean `takeAllLong` / `takeAllShort` (default `false`). When set, `decide()` short-circuits to `true` without calling `evaluate()`. Reason field set to `"take-all-long"` to distinguish in Excel output.
- **`latestEntryTime` in StrategyConfig gates entry by time of day** — a `String` field (`null` = no restriction). Enforced in `BacktestRunner.run()` after entry candle is resolved: if the entry candle's timestamp time part is after `latestEntryTime`, the trade is recorded as `NO_TRADE` with reason `"entry after latest-entry HH:mm"`. Prevents backtest from simulating trades that would be too close to square-off time.

## Chartink Strategy Design (Session 20 analysis)
- **The scan is a Wyckoff spring / failed-breakdown reversal (LONG bias)** — filter 6 (5m low < prev-day low) = stop-run below PDL; filter 7 (5m close > prev-day low) = price reclaims PDL; filter 3 (close == high) = no upper wick, buyers in control; filter 4 (5m low == daily low) = exhaustion point; filter 5 (range ≤ 0.5%) = tight controlled bar. Net: stock sweeps below PDL, prints the day's low, snaps back above PDL in a tight green bar. Requiring both cash AND futures = liquidity/institutional-interest confirmation.
- **Backtest strategies are post-alert overlays, not standalone strategies** — the 239 alerts are already filtered by the Chartink scan. The eight backtest "strategies" decide direction + SL/target on top of those curated alerts. `EMA_CROSS_V1` is not a true MA crossover; it checks close > EMA9 AND close > EMA21 (a momentum-reclaim filter). It works because the underlying alert already selected a spring setup.
- **BASELINE_VOL_SMA10 takes counter-setup shorts** — SHORT condition is red + vol<SMA10, which fires on a bearish signal inside a bullish scan. Those shorts are the primary drag on win rate and squareoffs. `BASELINE_LONG_ONLY` variant (no shortConditions) should lift win rate materially.
- **EMA_CROSS_V1 is the best scaler (highest Sharpe 0.153, highest net P&L 11.44%)** — carried by 2:1 RR. Adding ADX>22 should reduce the 6 consecutive-loss runs and 4.15% drawdown without gutting trade count significantly.
- **`close == high` in Chartink is exact equality** — valid on 5m bars where tick precision can produce an exact match. The backtest engine cannot replicate this; it has no per-bar structural op. Phase 2 `PrevDayLevelIndicator` is required for faithful entry replication.
- **To test more history: export a longer Chartink alert range** — `myapp.historic-data-days=5` seeds indicators only; the backtest window is determined by the alerts Excel file. For meaningful OOS validation export ≥6 months of alerts and use `?fromDate=` / `?toDate=` split.

## Backtest Capital Simulation + Monthly Breakdown (Session 22)
- **Capital return columns configurable via `myapp.backtest-capital-amounts`** — comma-separated list of `Long` values (default `10000,50000,100000,500000`). Spring Boot relaxed binding maps them to `List<Long>` in `ApplicationProperties`. `BacktestReportWriter` reads the list at write time and appends N columns to both the overall SUMMARY table and the monthly table. Column labels auto-formatted: `10000→₹10K`, `100000→₹1L`. Change the list in `application.properties`; no recompile needed.
- **Monthly P&L table in SUMMARY sheet below overall table** — 5-row gap between overall and monthly tables. Monthly table: Month | Strategy | Trades | Win Rate % | P&L After Charges % | Nifty Return % | Return ₹X.... Rows ordered Month ASC × Strategy sorted by expectancy DESC (same order as overall). Only months where `tradesTaken > 0` appear.
- **Nifty 1D candles fetched once, reused for overall + monthly returns** — `fetchNiftyReturn()` was replaced by `fetchNiftyCandles()` + `computeOverallNiftyReturn()` + `computeMonthlyNiftyReturns()`. Monthly Nifty return per "YYYY-MM" key: first and last 1D candle close in that calendar month; skips months with fewer than 2 candles (returns no entry, defaults to 0.0 in Excel).

## Analytics: Entry Gap + MFE/MAE (Session 25)
- **Entry gap = next candle open vs alert candle close** — reference point for "open confirmation": for LONG, ABOVE means the market gapped up into your direction before entry; for SHORT, BELOW is favorable. Threshold of 0.005% used for FLAT zone to filter tick-level noise. Computes for all rows (including NO_TRADE) since the next candle is always fetched.
- **MFE/MAE added to analytics, not backtest** — this is a research question ("does open confirmation improve win rate?") answered by filtering the analytics Excel. If stats are compelling, the condition can later be added as a backtest `ConfigurableBacktestStrategy` op. Premature to add to backtest before seeing the data.
- **MFE/MAE reuses `evalCandles`, no extra API call** — 1-min candles are already fetched in `buildRow()` for `TargetSlEvaluator`; the excursion loop runs over the same list from `evalEntryStartIndex`. For NO_TRADE rows where evalCandles is not fetched, excursion fields stay at 0/No.
- **Flag columns written as "Yes"/"No" strings, not 1/0** — existing analytics columns use 1/0 (vol flags, is_green etc.) but the new milestone flags use "Yes"/"No" for readability in Excel. No formulas in `updateStatsFormulas()` reference these new columns so there is no COUNTIF breakage.

## Alert Trigger Log (Session 21)
- **`AlertTriggerLogService` uses `Schedulers.boundedElastic()` not `CompletableFuture.runAsync()`** — `SlOrderStore` uses `CompletableFuture.runAsync()` (ForkJoinPool). The alert log uses `Mono.fromRunnable(...).subscribeOn(Schedulers.boundedElastic()).subscribe(null, errorLogger)` — more idiomatic for a WebFlux app; boundedElastic is the correct scheduler for blocking I/O; returns in microseconds so the trade path (candle eval, order placement) proceeds in parallel.
- **`CURRENT_CLOSE` backtest entry uses col D (first alert trigger price) from Excel, not candle close** — the "Triggered At" timestamp in `All_Triggered_Alerts.xlsx` is the second alert time; `findNearestIdx(candles, alertTime)` would land on the second-alert candle; using its close for `CURRENT_CLOSE` entry overstates slippage. Fix: `BacktestController.readAlerts()` reads col D as `firstAlertPrice`; `AlertEntry` record carries it; `resolveEntry()` uses it for `CURRENT_CLOSE` when `> 0`, falls back to candle close for rows where the user hasn't filled col D.

## EOD Squareoff & Registry Lifecycle (Session 28)
- **`EODSquareOffScheduler` iterates `getAllContextsSnapshot()` only** — the old code iterated both `getAllBuyContexts()` (byBuyId) and `getAllSellContexts()` (bySellId) separately; for a SHORT trade the same `OrderContext` lives in both maps, causing `squareOff(ctx)` to be called 2–3× and sending duplicate cancel requests to the broker. Fixed: single `Flux.fromIterable(getAllContextsSnapshot())` pass over `byBuyId` (the single source of truth). `getAllBuyContexts()` and `getAllSellContexts()` are kept on `OrderRegistry` for other potential callers but should not be used for squareoff iteration.
- **`squareOff()` uses CAS not plain read** — guard changed from `ctx.getTradeCompleted().get()` (non-atomic, both concurrent callers can pass) to `ctx.getTradeCompleted().compareAndSet(false, true)` (only first caller proceeds). The redundant `set(true)` inside the flatMap was removed.
- **`orderRegistry.remove(ctx)` enabled in all 4 exit fill strategies** — `SellFilledOrderStrategy`, `StopLossFilledOrderStrategy`, `ShortTargetFilledStrategy`, `ShortStopLossFilledStrategy` all call `orderRegistry.remove(ctx)` after `tradeCompleted.set(true)` in the success path. Removed only after the companion order cancel succeeds; if cancel fails, `markInconsistent()` is called and the context intentionally stays in the registry so EOD squareoff can still see and act on it. `OrderRegistry` was injected into the 3 strategies that previously lacked it.
- **WebClient `ConnectionProvider` with `maxIdleTime(10 min)`** — the AngelOne proxy server drops idle TCP connections after ~15 minutes (evidenced by `IOException: Connection timed out` at 15:15 for cancels sent at 15:00). A shared `ConnectionProvider` with `maxIdleTime(Duration.ofMinutes(10))` is used by both `directBrokerWebClient` and `proxyBrokerWebClient`. 10 min keeps connections warm across a typical burst sequence (alert → fill → SL/target placement, all within seconds–minutes) while safely evicting before the server-side drop. 30s was rejected as too aggressive for the SL/target placement latency window.
- **`OrderEventDispatcher` "No handler" changed from ERROR to WARN** — `cancelled` and `open pending` are normal WS statuses delivered during EOD squareoff and manual broker actions. Logging them as ERROR pollutes monitoring dashboards. Changed to WARN with message "No handler for WS status (ignored)".

## Disabled / Planned
- **Fallback LTP alert** (`fallback-alert-enable=false`) — fires a synthetic second alert using broker LTP when no real second alert arrives within `fallback-alert-wait-time-ms` (default 5300 ms). Implemented in `OrderService_v2.triggerLtpFallback()`. Fallback calls `handleAlert()` (full entry path including balance check) rather than `handleSecondAlert()` directly. Idempotency: the CAS (`WAITING → PROCESSING`) is owned by `handleSingleStockAlert`; the fallback does not claim it early. If real 2nd alert arrives before fallback fires, the scheduled task is cancelled at line 973. If real alert races with fallback LTP fetch, the CAS in `handleSingleStockAlert` ensures only one proceeds. For testing on weekends/non-market hours, set `fallback-ltp-mock-enable=true` and `fallback-ltp-mock-price=<price>` to bypass the live LTP API. Kept disabled by default because LTP can trigger the wrong candle condition on slow-moving stocks; only enable when you understand the trade-off.
- **Multi-stock batch fallback cleanup via `.doOnSuccess()`** — `handleAlert()` uses `Flux.concatMap(...).next()` which short-circuits after the first order is placed, leaving later stocks' fallback timers alive. Fixed by adding `.doOnSuccess()` that calls `alertStateRegistry.cancelFallbackIfPending(stock)` for every stock in the batch when a non-null `OrderResponse` is returned. Safe: no-op if task already cancelled; does not fire on first-alert batches (response is null).
- **JWT periodic refresh** (commented `@Scheduled` in `TokenManager`) — planned 15-min pre-expiry refresh via refresh token; disabled because AngelOne's refresh token endpoint was unreliable; current approach relies on startup login (token lasts the trading day).
- **Trading window gate** (`trading-window-enable=false`) — `ApplicationProperties` has the `tradingWindowEnable` field and time config; guard code exists but the flag is off to allow manual order testing at any hour.
- **`PendingOrderEventStore.replayPendingEvents()`** (commented out) — had a circular dependency: `PendingOrderEventStore` needed `OrderEventDispatcher`, which created a Spring cycle; replaced by inline `pendingEvents.remove() + dispatchDirectly()` calls inside `chartinkSimpleBuyOrder/SellOrder`.
- **`scheduleReconnectWithFreshToken()`** in `OrderWebSocketConnector` — dead code, duplicate of `scheduleReconnect()`; leftover from an earlier refactor; never called.
